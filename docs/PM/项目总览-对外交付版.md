# 校乐趣 · 项目总览（对外交付版）

> **代号说明**：MVP=最小可用版本（首版上线范围）；M0=启动前准备阶段（选型与需求冻结），M1=一期上线，S1~S3=第 1~3 个开发冲刺，T0=M0 启动日；P0=最优先级问题；D1~D8=八项结构性决策编号；UGC=用户发布的内容（社区帖子、二手、评论等）。
>
> 本文为可直接交付的完整文档：项目现状、范围与分期、人力与排期、外部依赖、合规要求、待确认事项全部在内，无需查阅其他文件。

## 一、项目现状

需求文档 1.0 是合格的梳理稿（17 章 + 80 张设计稿，用户侧 UI 全链路清晰），但不建议直接开工——离可开发的完整需求还差三层：后台管理层、平台层、非功能层。其中三个平台层卡点是硬阻塞：

| # | 卡点 | 性质 |
|---|------|------|
| 1 | **校园网/校园卡对接** | 难点不在开发，在数据源可能拿不到（依赖运营商/校方接口）——排期前必须先验证的第一件事 |
| 2 | **资金链路合规** | 平台涉及人民币归集与提现，属法律底线；走「担保交易」还是「不碰钱」需确定 |
| 3 | **UGC 内容审核** | 影响所有发布模块（社区/表白墙/二手/跑腿），不过审无法上架；默认方案为「先发后审 + 机审」 |

补齐方案已全部做完（默认规则 + 默认数值），当前等待需求方逐条确认（见第七节）。

## 二、范围与分期

| 期 | 范围 | 排除 |
| --- | --- | --- |
| 一期 MVP | 账号、首页、碎银、发布、校友圈、跑腿、订单、消息（8 个功能包） | —— |
| 二期 | 花名册、盲盒、校园活动、我的收藏/报名/邀请任务 + 数据报表/风控/财务对账完善/优惠券/IM 客服 | —— |

- 2026-10-13 确认：餐厅点餐、场景化扫一扫、商户客服归二期实现，需求定义随二期补齐；二期周期视定义补齐后的工作量重估。
- 自建与采购的边界：IM、推送、短信、机审、存储均可采购，选定供应商后为集成工作，不阻塞开发。必须自研且难度高的四块：校园网/校园卡对接、资金链路、碎银账本、跑腿交易闭环。
- 合规底线（上架前提，非可选项）：盲盒概率公示、账号注销、先发后审 + 机审、提现实名。

## 三、人力配置（2026-10-13 确认）

- 常驻开发组：**3 名后端 + 2 名 App**（跨端框架，一套代码双平台，分包并行）。
- 前端按固定节点接入（无常驻）：后台管理页面日常由后端接管（页面初稿借助辅助工具生成），复杂交互页（审核工作台等）在 S3 冲刺内进场约 2 周完成。
- UI 不驻场但交付节点固定：M0 期间完成一期 8 包设计稿切图标注，收尾阶段视觉走查约 1 周。
- 前端与 UI 的接入时间已写入排期里程碑，见[排期与里程碑计划『前端与 UI 接入安排』](排期与里程碑计划-给PM.md)。
- 增员建议仅 **+1 名测试**（专保资金链路与跑腿状态机回归）；加后端无收益（两条开发线均无余量）。
- 运营、客服、合规资质办理等非开发事项不在开发编制内；客服坐席建议首版用后台替代、不独立建端（待确认）。

## 四、投入前提与排期

1. 开发团队为兼职投入，常态档 **人均每周 3 天**（约 60% 投入，按满负荷测算）。本节全部周期以此档为前置条件——投入降档即重排，升档时重新评估后再定，不保证按比例压缩。
2. 周期：一期 MVP 约 **6.5~7 个月**上线，全量约 **9~10 个月**。周期已含必要余量（用于吸收外部环节波动与一般性返工），不单列拆分。
3. 服务端含 20% 测试时间（资金链路、跑腿状态机、碎银账本全量回归），后端线收口约 6.5~7 个月，仍在项目窗口内；App 端测试由开发自担，计入各冲刺。
4. 新增需求一律走变更流程排入二期清单，不在本计划周期内吸收；变更工作量另行评估排期。
5. M0 起点以八项结构性决策批完之日计（见第七节）。

## 五、里程碑总览（一期 MVP，T0 = M0 启动日）

| 里程碑 | 内容 | 出口标准 | 周期 |
| --- | --- | --- | --- |
| **M0 选型与冻结** | Flutter/RN 确定、资金方案确认、三方对接函发出、需求冻结 | 八项结构性决策批完；运营商对接函已发 | **3 周** |
| **S1 冲刺一** | 后端：账号体系/碎银账本地基；App：账号+首页+碎银；iOS 壳包提前提交一次过审，验证审核要求 | 登录/碎银获取消耗闭环可演示 | 7 周 |
| **S2 冲刺二** | 后端：跑腿状态机/担保交易/订单；App：发布+校友圈+订单+消息 | 核心交易闭环联调通过 | 7 周 |
| **S3 冲刺三** | 后台：内容配置+用户管理+审核工作台；App：跑腿双角色页；全员联调 | MVP 全功能回归通过 | 7 周 |

| **外部衔接窗口** | 运营商/校方接口、支付资质到位后的联调与切换（到位早则并入前序冲刺，不另占周期） | 三方联调通过 | 2~3 周 |
| **M1 一期上线** | | | **T0 + 6.5~7 个月** |
| **二期补全** | 花名册/盲盒/校园活动/收藏报名邀请 + 报表/风控/财务对账完善/IM | 全量功能 | 再约 3 个月 |

并行分工：后端 A（账本/订单/跑腿）、后端 B（账号/审核/后台管理面）、后端 C 兼架构（资金链路/三方接入）三人无依赖冲突；App-1（核心闭环包）、App-2（内容与交易包）分包并行互为 review。

## 六、外部依赖与周期说明

最大不确定项在外部，进度由外部机构决定，联调窗口按实际到位时间安排：

| 依赖 | 等待期 | 卡住时的降级 |
| --- | --- | --- |
| 运营商/校方接口 | 按以往经验通常需要 1~3 个月 | 流量数据人工月度导入；卡状态静态提示；碎银主渠道改任务/广告渠道 |
| 支付资质（商户号/分账） | 与运营商并行 | 降级方案「不碰钱」：提现/余额模块下线 |
| 苹果审核 | 每次提审 1~7 天 | 壳包 S1 即提交，提前消化隐私清单/Apple 登录问题 |

外部环节与开发并行安排：接口到位前开发照常推进，到位后进入对应联调窗口。

## 七、待确认事项（M0 冻结门，批完才进冲刺）

八项结构性决策，逐项确认后进入冲刺：

| # | 事项 | 建议方案 |
| --- | --- | --- |
| D1 | 校园网/校园卡接口可达性 | 无默认——全项目最优先验证项，数据源拿不到则核心价值降级；对接函 M0 内发出 |
| D2 | 资金链路方案 | 方案 A：担保交易（持牌分账通道）；备选：不碰钱 |
| D3 | 碎银↔人民币换算 | 1 两 = 1 元购买力（行业参考，上线前逐条核实） |
| D4 | 孤儿功能（餐厅点餐/扫一扫/商户客服）二期安排 | 归属二期已定；剩余为二期何时补需求定义、排期 |
| D5 | iOS/Android 交付方式 | 同步交付（现行排期按此测算） |
| D6 | 三方服务与云资源开通 | 机审选型（数美/易盾/网易盾三选一）+ IM 采购 + 云资源规格与开通主体 + 支付商户号申请主体 |
| D7 | P0 三项责任人 | 三个 P0 卡点各定一位责任人与截止时间 |
| D8 | 数据闭环推演缺口 | 数据推演中的推测项逐行确认，与设计意图不符处指出 |

另有三个执行层待确认项：客服坐席首版方案、碎银数值默认值逐条批注、审核模式 SLA。

## 八、技术形态（2026-10-13 确认，开发侧选型）

- 后端：Java 单体 + 云原生托管（模块化单体架构，预留多校 SaaS 演进）。
- App：跨端框架 Flutter（默认）/ RN（备选），最终待 App 人员背景确认。
- 后台管理：Vue + Element。
