# 云原生架构与部署方案

## 结论（给 PM）

- **定位**：本项目应用架构为**模块化单体**（Spring Boot），但基础设施与部署层**全量云原生化**——容器化交付、托管中间件、声明式 IaC、SaaS 可观测，符合 CNCF 云原生标准；**云原生 ≠ 微服务**，规模不需要的服务拆分是负债不是先进性。
- **为什么这样最先进**：3 人后端的全部产能花在业务（碎银账本/跑腿状态机/资金对账）上，控制面运维（K8s 自建集群/注册中心）托管给云厂商——**用托管换产能**是云原生在企业小团队侧的标准实践。
- **演进已内置**：多校 SaaS、服务拆分、独立扩容的触发条件已量化（§四），出现即升级，不需要推倒重来。
- **需要你拍板**：无架构决策待定项；资源规格见 §五，开通与用量由 PM 方与云厂商直接确认。

> 本方案是[技术栈与选型方案](技术栈与选型方案.md)的部署与基础设施篇；应用架构判定记录见该文 §一。

## 一、架构定位：云原生托管的模块化单体

```
┌─ 云原生能力面（CNCF 标准）────────────────────────┐
│  容器化交付   Docker 镜像 = 唯一交付物，环境零漂移      │
│  声明式 IaC   Terraform/云 ROS 管理资源，可复制可回滚   │
│  托管中间件   云 Redis / 云 MySQL / 对象存储+CDN       │
│  SaaS 可观测  日志·指标·链路三件套（开箱即用）          │
│  弹性伸缩     容器服务按 CPU/定时扩缩容                 │
├─ 应用架构面 ──────────────────────────────────┤
│  模块化单体   Spring Boot 3 多 module（账本/订单/     │
│              跑腿/内容/平台域），模块边界=未来拆分线    │
└──────────────────────────────────────────────┘
```

**为什么单体应用 + 云原生托管是这个规模的最优解**：单校场景峰值 QPS 50~150，瓶颈不在算力在**外部依赖**（运营商接口、机审回调、支付资质）——云原生的价值（弹性、托管、可观测）全部作用在我们真实的痛点上，而微服务化的代价（分布式事务/链路追踪/多套 CI）作用在我们没有的规模上。

## 二、云原生技术栈清单

| 能力 | 选型 | 说明 |
| --- | --- | --- |
| 容器运行时 | Docker + 多阶段构建 | 应用/后台同构交付 |
| 编排 | 云厂商**托管**容器服务（ACK 无服务器版 / TKE Serverless / 轻量 K8s） | 不自建控制面；起步可 Compose，单应用上线即入托管 K8s |
| CI/CD | 云效 / GitHub Actions → 镜像仓库 → 自动部署 | 提交即构建，主干可发布 |
| 中间件 | 云 MySQL（高可用版）+ 云 Redis + OSS/CDN | 托管：备份/高可用/监控出厂自带 |
| 异步与任务 | XXL-Job（容器内）→ 量大后换云消息队列 + 定时任务服务 | 碎银月结/T+1 对账/超时退款 |
| 可观测 | 云监控 + SLS/CLS 日志服务 + SkyWalking（按需） | 指标/日志/告警全托管，**外部依赖超时**（运营商/机审）必须有 trace 才能定界 |
| 配置中心 | Nacos 单机容器 / 云 ACM | 碎银数值规则（📊 项）热调整 |
| 弹性策略 | 定时伸缩（课间/晚间峰值）+ CPU 阈值保底 | 校园流量潮汐规律性强，定时策略比纯阈值更省 |

## 三、与外部依赖的云原生接法（本项目的真实难点）

| 外部依赖 | 接法 | 云原生能力落点 |
| --- | --- | --- |
| 运营商/校方接口 | 独立适配模块 + 人工导入保底通道 | 独立线程池隔离 + trace 定界 + 降级开关进配置中心 |
| 机审回调 | 异步回调 → 状态更新 | 消息队列削峰 + 重试幂等 |
| 支付/分账 | 持牌通道 API + T+1 对账 job | 对账差异自动生成工单，告警进 SaaS 监控 |
| 推送/IM/短信 | 全 SaaS SDK | 不占自建运维面 |

## 四、演进路线（触发条件量化，不搞先建设施）

| 阶段 | 架构 | 触发条件（任一命中即进入） |
| --- | --- | --- |
| 一期（现在） | 托管 K8s + 模块化单体 + 托管中间件 | —— |
| 二期 | 读写分离 + 账本模块独立扩容 | 日活 >2 万，或碎银接口 P99 >300ms |
| 三期 | 账本/订单拆独立服务，多校 SaaS 化 | 签约第 2 所学校，或租户隔离成为 PM 方硬性要求 |
| 不做 | 自建 K8s 控制面、服务网格 | 无触发条件——运维债换不来任何本项目指标 |

## 五、云资源规格清单

| 项 | 规格 |
| --- | --- |
| 托管容器（2 节点 Serverless） | 2C4G×2 |
| 云 MySQL 高可用版 | 2C4G |
| 云 Redis | 1G |
| OSS+CDN+日志 | 按量 |
| 三方 SaaS | 机审/IM 等，见自建服务评估 §二 |

> 规格按一期 MVP 峰值（QPS 50~150）给出；实际用量与供应商对接由 PM 方直接确认。

> 取舍记录：自建 K8s/微服务判否（S2 否决信号：运维负担超模块体量、无规模触发条件）；托管型云原生判可（容器/托管/SaaS 均为能力补齐，非权宜补丁，无需 PATCH 标记）。
