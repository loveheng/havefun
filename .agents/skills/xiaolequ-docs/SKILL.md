# 校乐趣0825 · 文档域表（项目数据）

规范机制（frontmatter / 切片命名 / Tombstone / 索引维护 / lint）见全局 skill `docs-spec` §1–§7，本文件只记项目数据，禁止复制规范正文。

## 域目录表

| 域目录 | 用途 | 现有文档 |
|---|---|---|
| `docs/requirements/` | 产品需求域：需求文档的评估、拆解、版本演进 | `requirements/需求文档评估.md`、`requirements/需求覆盖度清单.md`、`requirements/自建服务难度评估.md`、`requirements/数据闭环推演.md`、`requirements/缺失补全方案.md`、`requirements/端与交付物清单.md` |
| `docs/PM/` | PM 交付域（**派生域**）：从其他域文档提炼/汇总出来的面向 PM 的交付件，源文档在各自域才是正身 | `PM/PM结论汇总-给PM.md`、`PM/PM结论汇总-原始.md`、`PM/排期与里程碑计划-给PM.md` |

- 新域按实际出现登记；跨域架构/方案决策类文档落 `docs/decisions/`（按需创建）。
- **internal/ 与公共区的边界（硬规则）**：`internal/` 只放开发者视角的内部文档（工时评估、技术选型等），**不属于公域**；凡面向 PM 或对外交付的文档一律放公共区（`docs/`，PM 交付类落 `docs/PM/`），**禁止放 internal/**。放错位置=迁移，不迁就。
- **对外文档无价格（硬规则）**：价格预估与商务口径属**隐秘谈判环节**，不在日常文档中出现——`docs/` 下所有文档**不出现价格、成本、预算、报价、金额（¥/月费/年费等），也不出现人日/计价/结算/合同/付款/单价等商务口径词**，只谈业务。**合同类用词同样不进文档**：条款、双方、甲方/乙方、验收标准、承诺、违约、生效、签署、盖章等一律不用，改用「约定/说明/确认/前提」等平常说法。谈判底稿（结算方式、报价区间、让步梯度等）一律不落 `docs/`，仅可放 `internal/` 或口头/合同层面进行。采购/云资源类拍板项表述为「选型/规格/开通主体」；工期只挂投入档前置条件（如「人均每周 3 天」）；docs 中的工作量粗估只保留定性量级（低/中/高）。产品内经济玩法（碎银、订单付款、对账后台等）不在此列。
- **PM 域派生纪律**：`docs/PM/` 只放派生件，不承载原创需求/方案——新结论先落各自域的源文档，再派生进 PM 域；每个派生件须标注源文档与 updated 日期，**源文档实质修改后必须刷新对应派生件**（否则派生件与源脱节即失效）。
- **面向 PM 的评估/评审类文档**：首节固定 `## 结论（给 PM）`（≤5 行：判断 + 待拍板问题）；细节正文随后，裁剪交付只取该节。结论提炼由 AI 会话完成，不依赖脚本。
- **用词中性，不端着（写作基调）**：这些都只是评估和讨论稿，不是红头文件，更不是商业谈判文书——少用「定案」「机制」「口径」「原则」「纪律」「硬规则」「红线」「抓手」「赋能」这类官方/格式化词，用平常话把事说清就行（如「已确定」「这么定」「规矩是」）。判断可以直说，语气平实，不喊口号、不上价值。
- **不免责、不推责（写作基调）**：文档里不出现免责和推卸责任的话——不写「概不负责」「不承担…责任」「最终解释权」「责任自负」「因外部因素恕不…」这类话，也不把事情说成「都是对方/外部的问题」。风险就客观陈述事实和影响（如「接口没拿到则功能降级」），怎么分担在沟通里谈，不写进文档。
- **文档写完即自检（流程）**：每次实质修改 docs/ 文档后，跑 `toolbox run docs-word-scan` 机械自检禁用词。**扫描命中时先判断语境：属产品词汇（碎银、订单、跑腿、对账等业务本体）即放行**——把放行正则补进词表该行第三段（`scripts/agent-tools/docs-word-scan.words`），不为一时的命中去改产品文案；属商务/合同/官方用词则改写文档。词表随发现随补充，持续积累。
- 根目录 `需求文档.md` 为产品需求 1.0 原文（PM 协作对象，暂不迁入 docs/；迁入时按 docs-spec §2 三处同步）。
