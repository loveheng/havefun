# 技术栈与选型方案（结合需求）

> 前提：后端 3 人为 **Java** 技术栈；App 2 人技术栈待确认（选型分支见 §二）；后台管理页由后端接管（2026-10-13 定案）。本文对应排期 §6.5 的 M0 选型 3 周产出，依据[端与交付物清单](../docs/requirements/端与交付物清单.md)、[自建服务难度评估](../docs/requirements/自建服务难度评估.md)、[缺失补全方案](../docs/requirements/缺失补全方案.md)。

## 一、总体分层

```
用户端 APP（iOS/Android）  ← 跨端框架一套代码（Flutter 默认 / RN 备选）
        │ HTTPS / WebSocket(推送走三方SDK)
运营管理后台（Web）        ← Vue 3 + Element Plus（后端 B 接管，脚手架）
        │
后端服务（Java 单体）      ← Spring Boot 3 + MySQL + Redis + 定时任务
        │
三方服务（能买则买）       ← 短信/推送/IM/机审/对象存储/支付/广告
```

**形态决策：Java 单体服务，不上微服务。** 3 名兼职后端养不起注册中心/网关/链路追踪那套运维面；需求里各业务域（碎银/订单/跑腿/内容）耦合点是「碎银账本」一张表，单体 + 模块化分包（maven 多 module）即可支撑全量 ~9~10 个月的量级。拆服务的触发条件写死：碎银账本 QPS 或部署独立性成为瓶颈时再拆。

## 二、App 端：跨端框架（评估 P0 #1 在此定案）

| 选项 | 适配场景 | 本项目判断 |
| --- | --- | --- |
| **Flutter（默认推荐）** | App 人员无强 Web 背景，或从 0 组队 | UI 还原度高（80 张设计稿重交互）；Dart 上手成本低；双平台一致性好；Apple 登录/厂商推送插件生态齐全 |
| RN（备选） | App 人员有 React/JS 背景 | 选型前必须先确认人；热更新能力在国内受监管限制，不能作为决策依据 |
| 原生双端 | —— | 2 人分包并行做不了一套以上，**排除** |
| 小程序/H5 | —— | 推送、后台保活、支付体验均受限，且需求无小程序端，**排除** |

- 分包：App-1 核心闭环包（账号/首页/碎银/订单/消息/我的），App-2 内容与交易包（发布/校友圈/跑腿/花名册/校园网/二手）——与端与交付物清单 §6.1 一致，互为 review。
- App 内嵌 H5 不做：活动页等运营位若有，用跨端 WebView 容器兜底，不单独建前端线。
- **待确认（唯一选型分支）**：App 2 人的既有技术栈 → 熟 React/JS 选 RN，否则 Flutter。

## 三、后端：Java 技术栈明细（按需求块对应）

| 层 | 选型 | 对应需求/理由 |
| --- | --- | --- |
| 框架 | Spring Boot 3.x + Spring Security + JWT | 账号体系（补全 §3）：注册/登录/Token 标准件；微信/Apple 登录走 OAuth SDK |
| ORM | MyBatis-Plus | 团队主流；账本/订单类强 SQL 场景可控 |
| 数据库 | MySQL 8（单主 + 每日备份 + binlog） | 碎银账本/订单/跑腿全部强事务；量级用不着分库分表 |
| 缓存/锁 | Redis（验证码、排行榜、分布式锁） | **并发抢单**（跑腿 §11）用 Redis 锁 + DB 行锁双保险；流量排行榜用 ZSet |
| 状态机 | 枚举 + 事件表自管（不引框架） | 跑腿七态 + 订单四类；引入 Spring Statemachine 学习成本 > 收益 |
| 定时任务 | XXL-Job（或初期 Spring @Scheduled） | **碎银按月出账清零/有效期**（补全 §1）、资金 T+1 对账、跑腿超时退款 |
| 消息队列 | 初期不引；机审回调等异步点先用本地事件表 | 3 人运维面最小化；出现堆积再上 RocketMQ |
| 文件存储 | 阿里云 OSS / 腾讯云 COS + CDN | 二手 9 图+视频、Banner（采购，不自建） |
| 后台管理 | Vue 3 + Element Plus + 动态 RBAC | 后端 B 接管定案；权限分级+审计日志（B5） |
| 部署 | 云原生托管：Docker 容器化 + 云托管 K8s + 托管中间件 + SaaS 可观测 | 兼职团队用托管换产能；明细见[云原生架构与部署方案](云原生架构与部署方案.md) |

**关键实现要点（难点对齐需求）：**
1. **碎银账本**：流水表只增不改 + 余额表乐观锁；8 获取渠道/多消耗出口全部走统一记账接口，反刷规则（每日上限）在接口层拦截——评估 P1 #9 的落地位置。
2. **资金链路**：走微信服务商分账/持牌通道（缺失补全 §2），自建部分只有对账与退款工单；**绝不做二清归集**。
3. **机审异步化**：UGC 先发后审，机审 SDK 回调 → 更新内容状态 + 违规阶梯处置；敏感词库在后台管理（B2）。
